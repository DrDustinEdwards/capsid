# Backups and restore

D1 Time Travel already provides 30-day point-in-time recovery, so backups here are for longer retention and portability.

A daily Cron Trigger (09:00 UTC) exports the database to `MEDIA`:

- `backups/json/<timestamp>/<table>.json` one JSON dump per table, plus `_schema.json`, the CREATE statements `sqlite_master` held. The dump is [`@dustinedwards/d1-dump`](https://github.com/DrDustinEdwards/d1-dump), the package each site installs, so Capsid and the sites run one implementation. It dumps every table `sqlite_master` lists, skipping `documents_fts` and its shadow tables. Capsid excludes `d1_migrations`, wrangler's migration ledger. `TABLES` in `src/backup.ts` is the list the migrations create. A run whose dumped tables differ from it is refused as `tables-mismatch` and keeps its dumps unmarked, because the restore below knows only the migrations' schema. Retention is d1-dump's graduated default (`pruneDumps`, capsid/rulings/shared-homes-2026-10-06.md): the newest complete run of each of the last 14 days, 8 ISO weeks and 6 calendar months is kept, about 25 runs reaching back six months, and any other run is deleted whole. The newest complete run is never pruned, and nothing is pruned while no run is complete. A run is complete when it carries `_complete.json`, which is written last and only when the preflight passed; a run that threw mid-export or was refused has none, holds no slot, and is kept only while it is inside the 14-day window. A run with no marker counts as incomplete whatever its age: the carve-out for runs written before the marker existed (2026-09-25) is gone. `test/backup.test.ts` holds the wiring; the policy is tested in d1-dump.
- `backups/markdown/<namespace>/<path>` a plain-markdown mirror of every document body, one file per document, tracking current state (files for deleted documents are pruned).

After each export, `document_versions` rows older than 90 days and `audit_log` rows older than 180 are pruned. Pruning runs after the export, so every pruned row exists in at least one retained dump.

The private `DrDustinEdwards/capsid-backups` repository mirrors the JSON dumps off-account, so they survive loss of the whole Cloudflare account. Its workflow, schedule and retention live in that repository; this repo mints its credential at `POST /backup/credential` and observes the result.

**The watcher measures the mirror, and it measures the dump rather than the run.** Every half hour it lists `backups/json/` in that repo, resolved through the capsid namespace's `backups` mapping, and reads the newest directory name as the dump's own timestamp. Older than `MIRROR_STALE_HOURS` (36, the daily cadence plus slack) and it posts a finding, using the mirror workflow's latest conclusion to say which of three things happened: the workflow ran and failed, it has not run at all, or it ran green and no dump appeared. A GitHub it cannot reach posts nothing, because "cannot see the mirror" and "the mirror is dead" are different facts.

The dump is the signal because the attempt is not. The mirror was dead from 2026-09-09 to 2026-09-12, and on every one of those days it requested and received a valid backup credential before failing two steps later, so anything keyed on the credential reported it healthy. `MIRROR_STALE_HOURS` is deliberately not `BACKUP_STALE_HOURS`: that one is the local dump at 26 hours measured from a key this Worker writes, and the other repo's schedule can change without this one hearing.

Run one on demand with the admin credential, a write-grant `OPERATOR_KEY_HASH` key. A backup and its prune cover every namespace, so a minted agent is refused with 403 even when it holds write, and a missing or unknown key gets 401:

```
curl -X POST https://capsid.<your-subdomain>.workers.dev/ops/backup -H "Authorization: Bearer <key>"
```

## Restore

Three paths, in the order to try them. Path 2 has been executed end to end against a scratch database: all table counts matched the source and search worked on the restored copy. `restore-rehearsal.yml` runs d1-dump's restore drill on the newest R2 dump every Monday (see "The weekly drill" below).

1. **D1 Time Travel** (last 30 days, fastest), for fat-finger recovery or a bad bulk change. Run `wrangler d1 time-travel info capsid`, then `wrangler d1 time-travel restore capsid --bookmark=<bookmark>`. This rewinds the live database in place, so take a fresh bookmark first to keep the restore reversible.

2. **Table-scoped export and import**, for rebuilding into a new database. `wrangler d1 export` fails outright here, because D1 cannot export databases with FTS5 virtual tables. Export the real tables individually and data-only, taking the schema from the migrations:

   ```
   wrangler d1 export capsid --remote --no-schema --table <table> --output export-<table>.sql
   ```

   There are thirty-one real tables: `documents`, `namespaces`, `document_versions`, `audit_log`, `document_links`, the four improve-loop tables `improve_scores`, `improve_attempts`, `improve_runs` and `improve_skills` (`migrations/0003_improve.sql`), `jobs`, the work queue (`migrations/0006_jobs.sql`), `job_outcomes`, what each finished job produced (`migrations/0011_job_outcomes.sql`), `agents`, the scoped credentials (`migrations/0008_agents.sql`), `improve_jti`, the signed-request replay cache (`migrations/0004_improve_jti.sql`), and `skill_evaluations`, `skill_edits` and `skill_failures`, the skill lifecycle's evidence (`migrations/0012_skill_records.sql` and `migrations/0013_skill_attribution.sql`), `job_outcome_prs`, which pull requests an outcome counted (`migrations/0015_outcome_prs.sql`), `ops_sites`, the sites Capsid Portal watches (`migrations/0022_ops_sites.sql`), `ops_packages` and `ops_package_weeks`, the packages it watches and their weekly GitHub numbers (`migrations/0028_ops_packages.sql`), and `job_claims`, `job_evaluations` and `job_touches`, the claims dataset: what each agent said it did, each check of that against GitHub, and every human touch of a job (`migrations/0023_job_claims.sql`), `watcher_findings`, the watcher's memory of each finding across jobs (`migrations/0024_watcher_findings.sql`), and `agent_sessions`, `session_events` and `session_usage`, what Claude Code sessions reported by hook and telemetry (`migrations/0025_agent_sessions.sql`), and `task_runs`, the run ledger of every scheduled task (`migrations/0029_task_runs.sql`), and `job_versions`, the versions of a job that an edit replaced (`migrations/0033_job_versions.sql`), and `canon_proposals`, drivers' proposed changes to canon documents and who decided them (`migrations/0034_canon_proposals.sql`), and `shared_packages`, the shared packages the Portal's Shared code view follows (`migrations/0036_shared_packages.sql`). `TABLES` in `src/backup.ts` is authoritative, derived-checked against `migrations/` by `test/backup.test.ts`. Never export `documents_fts` or its `documents_fts_*` shadow tables: FTS5 derives them from `documents`, and they are what makes a whole-database export fail.

   Create the new database and apply every migration in order: `0001_init.sql`, `0002_document_links.sql`, `0003_improve.sql`, `0004_improve_jti.sql`, `0005_query_plan_indexes.sql`, `0006_jobs.sql`, `0007_jobs_resume.sql`, `0008_agents.sql`, `0009_jobs_required_scopes.sql`, `0010_console_indexes.sql`, `0011_job_outcomes.sql`, `0012_skill_records.sql`, `0013_skill_attribution.sql`, `0014_skill_status_index.sql`, `0015_outcome_prs.sql`, `0016_jobs_retry_cap.sql`, `0017_jobs_review.sql`, `0018_improve_unjudged.sql`, `0019_jobs_blocked_is_open.sql`, `0020_jobs_superseded.sql`, `0021_agents_job_binding.sql`, `0022_ops_sites.sql`, `0023_job_claims.sql`, `0024_watcher_findings.sql`, `0025_agent_sessions.sql`, `0026_outcome_pr_identity.sql`, `0027_job_summary_signature.sql`, `0028_ops_packages.sql`, `0029_task_runs.sql`, `0030_close_finished_job_mirrors.sql`, `0031_job_touches_admin_complete.sql`, `0032_job_model_routing.sql`, `0033_job_versions.sql`, `0034_canon_proposals.sql`, `0035_ops_sites_operator.sql`, `0036_shared_packages.sql`. Stopping early leaves later tables missing for the import to land in, and a column the code reads absent from a table that does exist. Then empty `ops_sites` and `shared_packages` with `DELETE FROM ops_sites` and `DELETE FROM shared_packages`: `0022_ops_sites.sql` and `0036_shared_packages.sql` seed them (and `0035_ops_sites_operator.sql` sets one row's operator), and the dump is each table's whole content, so a seeded row left in place would bring back a row removed since or collide with the dumped row on its key. The drill needs no such delete: it builds its scratch database from `_schema.json`, which holds no seed rows. The three claims tables are append-only, enforced by triggers that abort any UPDATE or DELETE of a row. They still restore, in the drill as here (it creates triggers after the rows): each is empty when the restore deletes from it, and a DELETE that matches no row fires no trigger. Then execute the exports with `documents` first: importing it fires the FTS sync triggers, so `documents_fts` rebuilds itself. The rest have no insert triggers and no foreign keys, so their order does not matter. Verify with count queries against both databases and one MATCH query on the new one, then point `wrangler.jsonc` at the new `database_id` and deploy.

3. **The R2 JSON dump**, beyond the 30-day Time Travel window. Wrangler cannot list R2 objects, so take the exact keys from the Cloudflare dashboard or the `json_keys` field of a `/ops/backup` response, then fetch each: `wrangler r2 object get capsid-media/backups/json/<timestamp>/<table>.json --file <table>.json`. Convert each object's `rows` to INSERT statements and follow path 2 from the create step, `documents` first. The same dumps are mirrored off-account in `capsid-backups`, so this path works if the Cloudflare account is gone. The `backups/markdown/` mirror is the last-resort human-readable copy: bodies only, no metadata.

   `_schema.json` rides beside the tables too. This manual restore takes the schema from the migrations and does not need it; the drill builds its scratch database from it. Two more underscore-prefixed sidecars ride beside the tables and neither is D1, so a restore that rebuilds the database and stops is incomplete:

   - `_kv.json` holds the loop's control pins, by allowlist: `improve_mode`, `improve:budget`, `improve:meta:last`, `backup:last-ok`, and per roster namespace its best record, pause reason and anchor checksum. Put them back with `wrangler kv key put` before turning the loop on, or every namespace runs unanchored. A `null` value means the key was unset; `{"unreadable": "<reason>"}` means the run could not read it, so the dump does not know its value and it must not be restored as unset. This is not a prefix sweep of `APP_KV`: that namespace also holds cached GitHub installation tokens, and a dump leaves the account.
   - `_holdout-manifests.json` holds each namespace's hidden-suite count, never a test. Without it every namespace scores as "no holdout manifest", which the scorer refuses.

   The dump is read in a single D1 batch, so its tables describe one instant. `document_versions` and `audit_log` are the exceptions in how they are read, not in what they hold: the batch reads each one's `MAX(id)`, and the rows up to that id are then paged and streamed to R2 as a multipart upload, because reading `document_versions` whole exceeded the isolate's memory from 2026-09-20. Both tables are append-only with an AUTOINCREMENT id, so the bound still describes the batch's instant. `documents` and `jobs` are updated in place, so they are still read whole inside the batch. Each file has the same shape as every other table's. `scripts/dump-invariants.mjs` checks the dump weekly and refuses a torn one.

## The weekly drill

`restore-rehearsal.yml` runs every Monday 11:30 UTC and on demand (`gh workflow run restore-rehearsal.yml`). It pulls the newest run from R2 with the minted object-read-only credential, then:

1. `node scripts/dump-invariants.mjs` reads the run directory and fails when `_complete.json` does not list exactly the files present, a sidecar (`_kv.json`, `_holdout-manifests.json`) is missing, empty or unknown, a table file's `table` field is not its file name, a row lost a column its siblings carry, `documents` is empty, or the dump is torn (a version row for a document created after the documents read, or a `write` audit row at or after the newest document naming a path not in the dump).
2. `npx d1-dump drill` (the restore drill in [d1-dump](https://github.com/DrDustinEdwards/d1-dump), the version `package.json` pins) restores the run into a scratch SQLite file (`--backend sqlite`, Node's built-in `node:sqlite`) named `restore-drill-<date>-<pid>`, then fails when the run is older than 26 hours, a table's rows differ from the marker, an external FTS5 index (`documents_fts`) holds a different number of documents than `documents` (counted through `_docsize`), a search for a word from a restored row finds nothing, any statement is over D1's 100,000 byte cap, a table's rows do not carry exactly the columns `_schema.json` gives it, or the scratch file could not be deleted. It deletes the scratch file whatever happened.

The drill replaces `scripts/restore-rehearsal.mjs`. Like it, the drill holds no Cloudflare credential: it restores into a local SQLite file, and the workflow sets no Cloudflare secret. That is a ruling (Dustin, 2026-10-05): a D1 Edit token covers every database in the account and cannot be limited to scratch databases, so a compromised action or a later workflow edit could delete production. What the sqlite backend cannot prove (D1's remote bound-value cap, its request limits, any difference between D1's SQLite build and Node's) is listed in d1-dump's README; capsid's values are bound, never literals, and every row in a dump was accepted by D1 when written. The same drill against a real D1 database is run by hand from the seat's machine, quarterly and after a change to the restore: `CLOUDFLARE_ACCOUNT_ID=... CLOUDFLARE_API_TOKEN=... npx d1-dump drill --dir <downloaded run> --backend d1`. A d1 drill killed before its cleanup leaves a database named `restore-drill-*`: list with `npx wrangler d1 list` and delete with `npx wrangler d1 delete <name>`.

Checks the old rehearsal made and where each lives now:

| Old check | Now |
| --- | --- |
| tables equal the migrations' tables, both directions | `tables-mismatch` at dump time (`test/backup.test.ts`, "tables-mismatch: missing none; unlisted stray"), and the drill restores exactly the tables the marker lists |
| table counts against the dump | the drill's `restore` and `counts` checks |
| FTS agreement through `_docsize`, and a search | the drill's `fts` and `search` checks |
| dump freshness, 26 hours | the drill's `dump` check |
| rows carry the table's columns | the drill (d1-dump v0.3.0 refuses a table whose rows lack, or add to, the columns `_schema.json` gives it, including a column missing from every row), and `dump-invariants` checks that every row carries the same columns |
| seeded rows emptied before import | not needed: the drill restores from `_schema.json`, which has no seed rows, and a leftover row would fail `counts` |
| sidecars, marker lists the files, shuffled files, torn snapshot, zero documents | `scripts/dump-invariants.mjs` |

The backup-safety rule is unchanged and lives in `src/backup.ts`: a destructive step (the prune) refuses unless `documents` is above zero and the pinned FTS probe matches.

Recovering one document rarely needs any of this: read its latest `document_versions` snapshot back.

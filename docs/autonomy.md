# Autonomy

What the machine may do with no human in the loop. Each policy lives in two places: a reviewable file in `docs/policy/`, and the copy the Worker actually reads, a signed document in the store. An unsigned copy, or one edited after signing, authorizes nothing.

Both ship with `enabled: false`, and **both are now on**: gates since 2026-09-13 under signature `a999f926`, auto-merge since 2026-09-16 under `dcde046a`. **The signed store document is the authority for that value, not this file.** Turning one on is a ruling that lands in the audit log, and nothing in this repo is gated against it: this paragraph read "Both policies ship disabled" until 2026-09-16, by which point it had been wrong about gates for three days.

**Auto-merge** (`docs/policy/auto-merge.md`, read from `capsid/policy/auto-merge.md`).
The five-minute tick walks every open pull request on the namespaces the policy names
and merges only those that pass all twelve checks, evaluated in order, each refusing on
its own. **A merge is a deploy on any repo that deploys on merge to its default branch**,
so passing these checks there ships to production with no human. The live signed
policy is version 7 and names dustinedwards, carrel, capsomer and capsid. capsid was taken out on 2026-09-25 because a
capsid merge deploys the control plane, put back with no limit on 2026-10-07, and limited
by version 6 (D6 of 2026-10-03, confirmed 2026-10-09) to docs-only PRs outside
`docs/policy/` and dashboard CSS-only PRs; its tests, Portal scripts and every other path
wait for the seat. carrel and capsomer joined for auto-merge only on 2026-10-08.
Version 7 (job_e68de044f8a4, 2026-10-10) makes the pull request the claim: it drops
`author_is_driver`, so a job a cloud session completed without a claim can merge, and
adds `size_within_cap`, so a pull request over 1,000 changed lines waits for a person's
approval.

| check | what it requires |
| --- | --- |
| `paths_not_refused` | the changed-file list was read whole, and no path matches the policy's refused paths: the policy and signer sources, the protected path list, migrations, wrangler config, secrets, the files that define the checks, and the two sources that write what `pr_recorded_for_job` reads |
| `paths_not_money` | no changed path names a billing or payment surface |
| `no_migration_workflow_lockfile` | no changed path is a migration, a workflow or a lockfile |
| `paths_allowed_for_namespace` | for a namespace with allowed paths (capsid: `docs/` outside `docs/policy/`, and `dashboard/**/*.css`), every changed path, old names of renamed files included, is inside them |
| `head_in_base_repo` | the PR's head branch is on the base repo, not a fork |
| `body_names_job` | the PR body carries the id of the job the work came from |
| `pr_author_allowed` | the GitHub account that opened the PR is on the signed document's author allowlist (`DrDustinEdwards` and `capsid-repo-access[bot]` in version 7) |
| `job_handed_on` | that job is `blocked` or `done` |
| `pr_recorded_for_job` | the job's `result_ref` or one of its `job_outcome_prs` rows names this PR |
| `base_is_default_branch` | the PR targets the repo's default branch |
| `size_within_cap` | the PR changes at most 1,000 lines (additions plus deletions); a larger one is merge class `approve`, "over the size cap" |
| `ci_green` | every check run on the head sha completed and concluded success, skipped or neutral, at least one reported, and the CI run on that sha ran the typecheck step (all four configs), the lint step, the unit suite and the integration suite to success |

Tests, `src/`, docs, `CLAUDE.md` and `.claude/` pass the refused-path check since policy version 2 (2026-09-17); in capsid, version 6 then holds all but docs and dashboard CSS for the seat. `PROTECTED_PATH_PATTERNS` (`src/protected-paths.ts`), once the improve loop's list and now the paths a repo write needs `can_touch_protected` for, no longer decides what auto-merges.

The document names the checks, the refused paths, the allowed paths and the required CI steps, and the code
enforces them. A document that disagrees with the code on any of the four is refused at load time. A test asserts the two agree in
both directions. The PR author allowlist is the exception: it is carried only in the
signed document, the code holds no copy, and a document that names no author does not
load. A pull request failing any check is left open, audited with the check
that refused it, and reported under `capsid_run_improve` action `status` as awaiting the seat.

**Pre-approved gates** (`docs/policy/gates.md`, read from `capsid/policy/gates.md`). A
driver that reaches a push, a migration or a pull request blocks with the exact command,
and every one of those waits on a person. This policy lets the seat send a bounded one
back itself: `capsid_work_jobs` action `resume` with `approved_by_policy` set to the document's
version, refused unless the blocked command matches one of three classes. A driver may
do the same for a job it blocked itself, but only when every class matched is
`push_branch` or `open_pr` (ruled 2026-09-16). A migration stays the seat's to approve,
and a driver cannot approve another agent's job. Outside the policy, a driver cannot
resume a blocked job at all: a plain resume is refused unless the caller is the admin or
holds `can_merge`, for the job's claimant (2026-09-25) and for any other driver in the
namespace (Grok audit 2026-10, S1).
`additive_migration` is a `wrangler d1 execute` naming a `--file` under `migrations/`
whose every statement is `CREATE TABLE IF NOT EXISTS`, `ALTER TABLE ... ADD COLUMN` or
`CREATE INDEX`. An unrecognized statement form is a refusal, not a pass.
`push_branch` is a `git push origin <branch>` for a branch that is not `master` or
`main`, with no force flag. `open_pr` is a `gh pr create`. A never-list is checked over
the whole command before any class is tried: secrets, revocations, force pushes, pushes
to a default branch, `wrangler deploy` and `rollback`, mode changes, drops and deletes,
and merging a pull request, which the auto-merge policy governs instead. The audit row records which
class matched and what it matched on.

**Signing is admin only.** `capsid_admin_control_improve` action `sign_policy` signs the body already
stored rather than any body the caller supplies, only in the `capsid` namespace and
only under `policy/`. A minted agent is refused outright. Turning a policy on is
two acts: editing the document, which is on the ordinary write tool's refusal list and
needs `allow_improve_paths` plus `can_touch_protected`, and signing it again afterwards.

**Only the body signed last loads.** `sign_policy` records the sha256 and version of the
body it signs in APP_KV under `policy:signed:<path>` before it stores the document, and
both loaders refuse a signed body with any other hash. An older signed version put back
with `capsid_write_doc` action `restore` or a write is refused until it is signed again. Re-signing the same body
writes the same record. When the key is absent (the first load after this shipped, or
after the key is deleted), the load records whatever signed body is stored at that
moment. The key is not in the backup's KV pins: after a D1 restore to an older policy,
the loaders refuse it until the seat signs it again.

**Sessions start in the cloud** (docs/routines.md): a routine fires a session for a queued job, the job is marked started, and the session completes it by naming its pull request. The overnight switch and the plan and digest views are in docs/overnight.md.

**Merge classes, report-only** (`src/merge-class.ts`; docs/design/design-merge-pipeline.md section 2, the design's PR 2, ruled 2026-10-09). The tick gives every PR it judges one class with its reasons: `auto` (passes the signed policy), `approve` (stopped only by a rule a person may waive), `typed` (any money path, decided before anything else), `seat` (a migration, a workflow, a fork head, a base other than the default branch, or a file list that could not be read) or `wait` (CI not finished, or a draft). Its path class is its riskiest file's: docs, dashboard-css, tests, dashboard-code, deps-own, src-routine, deps-other, src-worth, workflow, migration, money (a manifest or lockfile counts as deps-other until the diff is read). The class, path class and reasons ride on the awaiting-seat set and in the inbox item's title. The approval record reads them, and the executor merges what was approved (both below). A PR whose body names no job is not read, so it has no class. Tests: test/merge-class.test.ts, and the tick's in test/auto-merge.test.ts.

**The approval record** (`src/pr-approvals.ts`, table `pr_approvals`, migrations/0037; the design's section 3 and PR 3). The admin approves one or more pull requests at the head sha reviewed through the `approve_pr` control: in the Portal, or in chat through the `capsid_admin_run_controls` tool (`perform approve_pr {namespace, prs: "312,315", shas: "<sha>,<sha>"}`), so no tool is added. It records and never merges. Each PR's class comes from the awaiting-seat set: `approve` (and `auto`) may be approved; `typed`, any money path, only alone and only with its number typed as `confirm`, and it is recorded with surface `typed`; `seat`, `wait` and a PR the tick has not classed are refused. A batch with one refused PR is refused whole. The head is read from GitHub at preview and again at perform, and must start with the sha named, so a push since review is not approved. One open approval per PR (a partial unique index): approving again voids the open one as `replaced`, and the control's Undo voids it as `undone`. Each move is `UPDATE ... WHERE id = ? AND status = 'approved' RETURNING id` and writes `pr-approved` or `pr-approval-voided` beside the click row. Tests: test/pr-approvals.test.ts, and the control through the Worker in test-integration/portal-actions.test.ts.

**The executor** (`src/approval-executor.ts`; the design's section 4 and PR 4). The tick is the only thing that merges an approved PR. After its policy pass, for a PR the signed policy left open that holds an open approval, in order: a head that is not the approved sha voids it ("new push"); an approval 7 days old expires; CI on that sha is judged by the policy's own `ci_green` test with its required steps (`ciGreenOn` in `src/auto-merge-policy.ts`), so CI still running waits, red CI voids it ("CI red"), and a namespace with no required steps refuses it; a head off the base repo, a base that is not the default branch, or a money path approved without its typed confirmation refuses it; otherwise it merges with method `merge`, pinned to the approved sha, so a 409 voids it ("head moved") and success moves the row to `merged` with the merge sha. A PR the policy merges on its own closes its approval as merged. An approval on a PR the tick no longer sees (closed or merged by hand) expires at 7 days in a sweep at the end of the tick. Each move is one `UPDATE ... WHERE id = ? AND status = 'approved' RETURNING id` in one batch with its audit row (`approved-merged`, `pr-approval-voided`, `pr-approval-expired` or `pr-approval-refused`, written as `improve-loop` like the tick's own rows). A tick that cannot read the approvals goes on as the policy alone. Tests: the tick's in test/auto-merge.test.ts ("the executor").

## Earned promotion and demotion

The merge pipeline's units (`src/merge-units.ts`; docs/design/design-merge-pipeline.md section 7; Dustin's DECIDE 9 and 10 of 2026-10-09). A unit is a namespace and a path class (`src/merge-class.ts`: docs, dashboard-css, tests, dashboard-code, deps-own, src-routine, deps-other, src-worth, workflow, migration, money). This is **report-only**: it proposes, and nothing here widens what merges unattended.

- **Evidence, per unit, over 90 days:** approved merges from `pr_approvals`, which records each approval's namespace and path class since `migrations/0043_pr_approvals_unit.sql` (older rows count toward no unit); approvals voided for anything but a new push (an undo, red CI); and rollbacks from `deploy_outcomes`, placed in a unit through the tick's `auto-merged` audit row (which carries `path_class` since this change) or the pull request's approval; and reverts of pull requests the tick merged, from the `auto-merge-reverted` rows the safety meter records (below): a revert counts like a rollback of an unattended merge, suspending its unit and blocking its promotion.
- **Promotion proposal:** at least 20 approved merges over at least 14 days, no rollback or revert, and at most one approval voided for anything but a new push. It reaches Needs you as an inbox item of kind `proposal`, "Promote capsid tests to auto: 24 approved over 30 days, 0 rollbacks". Acting on it is `sign_policy_change`, below.
- **Demotion:** a rollback of a pull request the tick merged unattended suspends its unit at once (KV `merge-units:suspended`, an `audit_log` row `merge-unit-suspended`). The auto-merge tick then holds back anything the policy would merge in that unit: it is declined as `unit_suspended` and falls to class `approve`, so it merges only on Dustin's approval. A suspension list the tick cannot read holds every unit back for that tick. The inbox shows the suspension and a proposal to remove the unit from the signed list. A rollback of an approved merge suspends nothing, but blocks its unit's promotion.
- **Promoting or removing a unit:** the admin control `sign_policy_change` (`src/policy-sign.ts`; params `change` promote or demote, `unit` such as `capsid/tests`, and `confirm`). Its preview reads the signed policy in force, which must load, and shows the next version with one line of the `## Auto units` section added or removed. The perform signs and writes that version (the anti-rollback pin first, then the prior version snapshotted and an `audit_log` row `policy-changed` in one batch), and only when the new version number is typed as `confirm`: it widens autonomy. A unit is written `- unit \`<namespace> / <path class>\`` under `## Auto units`. A document naming an unknown path class, money, a migration, a workflow, a namespace the policy does not cover, a unit twice, or a unit outside that section loads nothing. A promoted unit widens only `paths_allowed_for_namespace`: a PR whose path class (the riskiest of its files) is a listed unit of its namespace passes that check, and every other check, refused paths and money included, still applies. A suspension still holds a promoted unit back.
- **Signing the policy from the repo:** the admin control `sign_policy_from_repo` (`src/policy-sign.ts`; param `confirm`), with its panel "Auto-merge policy" on the Portal's Pull requests page, whose "Load from repo and sign" button opens it. Its preview reads `docs/policy/auto-merge.md` from the capsid repo's default branch (fresh, not the read cache), holds it to every check `loadMergePolicy` makes (`checkMergePolicyBody`), refuses a file that opens with frontmatter, is not a newer version than the stored policy, or is the policy already stored, and shows the old and new sha256 of the body and the lines removed and added. The token binds the hash it read. The perform reads the file again and is refused if it hashes differently, or if the typed `confirm` is not the file's version; then it writes and signs the file exactly as it reads, through the same path as `sign_policy_change` (the anti-rollback pin first, then the prior version snapshotted and an `audit_log` row `policy-loaded-from-repo` in one batch). The stored policy in force need not load, so this also replaces one that does not. The panel shows whether the Worker loads the policy now and, if not, why.
- **Lifting a suspension:** the admin control `unit_resume` (params `unit` and `reason`) clears the unit from `merge-units:suspended`, records when it was lifted (`merge-units:lifted`, so the rollbacks before then suspend it no more, while a later rollback suspends it again) and writes `merge-unit-resumed`.
- **The reviewable copy:** `docs/policy/auto-merge.md` stays at the version it shows until the seat copies the signed store document back into it after a change, as for any signed policy.

The tick's `merge-units` step runs every five minutes after the watcher and is recorded in the run ledger only when its report or a suspension changed. Money paths stay class `typed` whatever the record says (design section 8).

## The safety meter, the shutoff, and existing tests

Three narrowings the tick applies outside the signed policy, as it does a unit's suspension. They only hold pull requests back for Dustin, so they need no new policy version and change neither `POLICY_CHECKS` nor `docs/policy/auto-merge.md` (`src/merge-safety.ts`; docs/design/design-merge-pipeline.md section 7, "Safety meter and shutoff"; job_cd5ffb1f87b4). No D1 migration: `audit_log` rows and `APP_KV`.

- **Revert tracking:** at most every 30 minutes (KV `merge-safety:reverts-last`), for each namespace the signed policy covers, the 50 most recently updated closed pull requests are read. A merged one that reverts a pull request the tick auto-merged (GitHub's `Reverts owner/repo#N`, `revert #N` or `reverts #N` at the start of its title or of a body line, or `This reverts commit <sha>` matched to the merge's `merge_sha` or `head_sha` by a prefix of 7 or more hex characters) writes one `audit_log` row `auto-merge-reverted` (`repo`, `pr`, `reverted_by`, `path_class`, `merged_at`), once per reverted pull request and revert. A GitHub failure for one namespace is logged and the rest go on.
- **The meter:** every tick, per namespace over the last 7 days: `auto_merged`, `approved` (approved by Dustin, leaving out the duplicate row a policy merge writes when it closes a held approval, as `src/trends.ts` does), `deploys_verified`, `rolled_back`, `rollback_failed` and `reverts`. The report is kept in KV `merge-safety:report`, and `capsid_run_improve` action `status` (`merge_safety`), the Portal feed (`live.merge_safety`, the CI view's "Auto-merge, last 7 days") and the phone alerts read it with no D1 or GitHub read.
- **The shutoff:** a namespace pauses when 2 or more of the pull requests the tick merged were rolled back or reverted in 7 days (one pull request counts once, however many deploys or reverts it drew), or when that 7-day rate (bad over unattended merges, merges floored at 1) is more than 3 times the rate over the 30 days before (days 7 to 37). The rate rule needs a nonzero baseline, at least one bad event and one unattended merge in those 30 days; with a clean baseline only the count rule applies. The pause is KV `merge-safety:paused` and an `audit_log` row `auto-merge-paused` (actor `capsid:merge-safety`), and it sends one phone alert. The auto-merge tick then declines anything the policy would merge there as `namespace_paused`, class `approve`, reason "auto-merge for <namespace> is paused: <reason>"; a value it cannot read pauses every namespace for that tick. Dustin's approvals still execute.
- **Resume:** the admin control `automerge_resume` (params `namespace` and `reason`, the reason required) clears the pause, records when (`merge-safety:lifted`, so the events before then count no more, while later ones pause it again) and writes `auto-merge-resumed`.
- **Existing tests always wait for Dustin:** a pull request that changes an existing test under `test/`, `test-integration/` or `dashboard/e2e/` is never merged unattended, whatever units are promoted. An edit is a file there that is removed, renamed away, or modified with any deleted line, and one GitHub reports without a status or without an integer `deletions` (fail closed). A file added whole, or modified with only added lines, is not an edit. Such a pull request is class `approve` with the reason "changes an existing test: <names>" first, and the tick declines it as `changes_existing_test`. Dustin's approval still merges it.

The tick's `merge-safety` step is recorded in the run ledger only when it recorded a revert, paused a namespace or changed the meter.

## The watcher

A half-hourly step on the five-minute tick that reads the surface and, when something needs a person, posts a job. That is all it does. It holds no blast-radius flag, it is scoped to `capsid_work_jobs.post`, and it cannot claim what it posts or fix what it found.

- **What it reads.** `/health` against master (degraded store, a deployed sha that is not master head, a backup older than the window or that never ran, a live schema behind the newest migration); `capsid_run_improve` action `status` (a namespace whose queue circuit breaker is open); CI on each roster repo's default branch, red for more than two hours; and the off-account mirror, where it reads the newest dump directory under `backups/json/` and reports a dump older than 36 hours, naming which of three things happened from the mirror workflow's latest conclusion. The mirror check keys on the dump rather than on the run, because during the 2026-09-09 outage the mirror requested a valid credential and its run started every day while nothing landed. The live checks (`docs/live-checks.md`) read what `capsid/policy/live-checks.md` names: a site's deployed sha against its default branch, and the Web Analytics beacon and CSP on its pages. With no such document they do not run.
- **Only actionable findings post jobs** (job_2c92174d5bff item 5; every alert actionable, the rest to a digest). Each fingerprint pattern has a class beside `OWNERS` in `src/watcher.ts` (`findingClass`), and `test/watcher-classes.test.ts` fails when the two tables disagree. **job**: site down, error rate, deploy rolled back or rollback failed, stale or never-run backup and the mirror findings, domain expiry, CI red over two hours, schema behind, degraded health, deploy drift, site map drift, unmapped repos, an invalid or unknown-site live-checks config, an unhealthy site after self-repair. **digest**: CSP, security headers, analytics setting and beacon (`live-*` other than the config findings, including `live-sha-*` and the unread-page findings), `site-weekly-*` and stale canon (`stale-canon-*`). **attention**: agent anomalies (`anomaly-*`) and open queue breakers (`breaker-open-`). A digest or attention finding is still recorded in `watcher_findings`, open with no job, so the Portal can show it and a clear works; it posts nothing. An open queued job for a finding that has become digest or attention class is failed as `cleared: moved to the weekly digest` (or `the Portal's attention list`) on the next pass, through the same keyed clear and audit (`job-cleared`) as a gone finding; a claimed or blocked job is left to its holder. The weekly digest per site is the open digest-class rows grouped by namespace: the Portal's Needs you page shows it as the Weekly digest panel, and the daily email (docs/portal.md, "Daily digest") adds the same list on Mondays UTC.
- **A healthy surface posts nothing.** A pause a human set is not a finding.
- **Agents out of pattern** (`src/anomaly.ts`, OWASP item 6; Dustin, D4 of 2026-10-03). Each pass reads audit_log for minted agents (`agent:*`, the watcher itself excepted), counted per actor, action and hour, and compares the last 24 hours with the 14 days before them. A finding when an agent writes an action it never wrote in its baseline (`anomaly-new-action-<agent>-<action>`); when its busiest hour is over three times its busiest baseline hour and at least 30 rows (`anomaly-rate-<agent>`); or when an agent with no baseline is first used between 00:00 and 06:00 Chicago time (`anomaly-first-use-<agent>`). A hit is a finding and a warning row in the Portal's Needs attention, nothing more: nothing is suspended or revoked until two weeks of false positives are measured (a person who fails the finding's job as expected adds to that count). A hit clears itself once it falls out of the 24-hour window. What writes no audit row (most reads) is not seen. Tests: test/anomaly.test.ts, test-integration/anomaly.test.ts.
- **Domain registrations** (`src/domain-expiry.ts`; job_5ac1139641e0, design-portal-insight.md section 5, pulled forward by Dustin on 2026-10-07). The registrable domain of each configured site's origin (hosting suffixes such as workers.dev and vercel.app left out) is read by RDAP: the IANA bootstrap (`data.iana.org/rdap/dns.json`, kept a week in KV) names the registry's server, and its `expiration` event is kept a day, so a domain costs about one RDAP call a day. A finding 30 days before expiry (`domain-expiry-30d-<domain>`) and a new one 7 days before (`domain-expiry-7d-<domain>`), so the last week posts again even if the first was dismissed. A domain that could not be read is logged (`WATCHER_DOMAIN_UNREAD`) and the check does not count as run, so an open finding is never cleared by a failed read. Tests: test/domain-expiry.test.ts.
- **Stale canon after a merge** (`src/stale-canon.ts`; improvement item 23). Each pass lists every mapped namespace's newest closed pull requests (primary repo, 20 per list, at most 20 namespaces) and reads the files of up to 5 new merges into the default branch, kept in `APP_KV` under `stale-canon:merges` for 30 days. A canon document (a canon path in `src/canon.ts`, or type core, spec, protocol, procedural or reference; never `archive/`, `research/`, `reports/`, `audits/`, `jobs/`, superseded or closed) is flagged when it cites a file a merge deleted or renamed, by path in its body or by a typed edge to `<namespace>/<path>`, or has an edge to a file a merge modified. One digest finding per document and pull request (`stale-canon-<namespace>-<pr>-<tag>`), naming the document, the pull request and each cited path. Nothing is rewritten. A document written after the merge is not flagged, so writing it, dropping the citation or the merge leaving the window clears the finding. A document that describes the old behaviour in words without a path is not caught. Tests: test/stale-canon.test.ts.
- **Deploys** (`src/deploy-outcomes.ts`, table `deploy_outcomes`, migrations/0039; docs/design/design-merge-pipeline.md section 6, PR 6). For each deploy roster repo (the five app repos plus carrel), the newest three completed push runs on its default branch: a run whose job named "live gate" (or "<caller job> / live gate" when the gate runs in a called workflow such as devkit's worker-deploy.yml, as carrel's does) ran is recorded once as `verified`, `rolled_back` (with where production went, from the rollback step's annotation), `rollback_failed` (the rollback did not take effect), `rollback_skipped` (the guard declined to roll back) or `unverified` (the gate failed with no rollback), with the pull request GitHub links to the commit. GitHub serves no step summary through its API, so the outcome comes from the job's conclusion, its rollback step's conclusion and its check-run annotations. A known run is read from D1, not GitHub. The newest recorded deploy raises a finding when it was rolled back (`deploy-rolled-back-<namespace>`) or its rollback did not take effect (`deploy-rollback-failed-<namespace>`); a later verified deploy clears it. The check counts as run only when every repo was read. No CI secret is added: the App already reads CI. Tests: test/deploy-outcomes.test.ts and test-integration/deploy-outcomes.test.ts.
- **Deduplication.** The finding's fingerprint goes in the job title, and `post` refuses a duplicate while one is open. A finding that stops being found has its job failed with `cleared`, keyed on `queued` so a job a driver has claimed is never closed underneath it.
- **Finding memory.** An open job alone forgot a finding the moment a person ended it: the site-map drift finding was filed again within an hour of the seat superseding it. So the watcher keeps one row per fingerprint in `watcher_findings` (`src/watcher-findings.ts`, migration 0024), across jobs, in one of three states:
  - **open**: its job is open (a digest or attention finding is open with no job). Each pass that sees it adds one to `seen_count`, sets `last_seen_at` and appends the evidence, keeping the newest 20 sightings. Nothing is posted.
  - **dismissed**: its job left the open set some way other than the watcher's own `cleared` (superseded, failed, done) while the condition still held. The person's ending holds: the finding is counted and not filed again until it clears.
  - **cleared**: its owning check ran and did not see it. `cleared_at` is set, and `reopen_after` is six hours later (`REOPEN_QUIET_MS`, the quiet period). A cleared finding seen again inside the quiet period is counted and not filed; seen after it, it is filed as a new job and the row is open again. A dismissed finding that stops being seen clears the same way.

  A finding with no row is filed. An open job with no row (posted before the table) is adopted rather than filed again. Every write is keyed on the fingerprint, and a state move is guarded on the state it was read in, so the tick and the Portal's Refresh cannot both move a row; a lost move is logged as `WATCHER_FINDING_MOVED`.
- **CI red is one incident per namespace.** The fingerprint is `ci-red-<namespace>`, and the head sha of each sighting is evidence. It carried the sha until 2026-09-29, and ci-red was filed 13 times between 2026-09-20 and 09-23 as each red commit became a new finding.
- **Cadence** is `watcher:cadence-minutes` in `APP_KV`, 30 by default, with a floor of 5. It rides the tick after auto-merge. It spends no model tokens and no CI minutes.
- **It keeps each pass in `ops:snapshot`** (`APP_KV`, `src/ops-snapshot.ts`), the data the operations dashboard reads (capsid/research/design-ops-console.md). The snapshot holds:
  - every check as clear, finding or could not run;
  - `/health`;
  - the mirror's newest dump and last run;
  - each roster repo's latest CI run;
  - the Portal's site configuration compared with the registered namespaces;
  - a probe of every configured site (`ops_sites`, docs/portal.md), and none when nothing is configured;
  - Cloudflare's view of each site: its last ten deploys and 24 hourly buckets of requests and errors.

  **Probes.** Each site's health route is read, or its root where it has none, and the root as well when the health route fails. So a broken health route on a site that is up reads as degraded, not down. Capsid itself is read in-process.

  **Uptime ring.** Each site keeps a 7-day ring of half-hour slots aligned to the clock. A slot no pass reached is marked as no data, never as up.

  **Reading it over MCP.** `capsid_admin_read_ops` action `snapshot` (admin only) returns the snapshot whole, or one site's entry with `site`, or one half-hour slot of that site's ring with `site` and `slot` (0 the newest, up to 335) or `at` (an ISO time). A slot reads `up`, `down`, `no-pass` or `outside-ring` (older than the history the ring holds yet), with the half hour it covers. No snapshot yet, or one that does not parse, is a named error.

  **Write order.** The snapshot is written before `watcher:last`, so a snapshot that cannot be written fails the pass and the next tick runs it again.

  **Site map.** A registered namespace the map neither covers nor lists as having no site, or a map entry whose namespace is not registered, is a finding.

  **Cloudflare.** `src/ops-cloudflare.ts` reads Cloudflare once per pass, never per dashboard request, with `CF_OPS_TOKEN`, a read-only token holding Workers Scripts Read and Account Analytics Read (and Workers CI Read for `capsid_admin_read_ops` actions `builds` and `build_logs`, docs/portal.md, "The Cloudflare token"). The account is `CF_ACCOUNT_ID`, or `R2_ACCOUNT_ID` where that is unset. A site's script is named in the map only where the host proves it (a `workers.dev` host's first label); any other site is resolved from the account's Workers custom domains, and one that resolves to nothing is shown as unresolved, never guessed. Deploys come from the script's deployments list. Errors come from one GraphQL Analytics query for every script (`workersInvocationsAdaptive`). A query that fails is shown as no data with its reason, never as zeros. With no token nothing is fetched, each site says what is unset, and the `cloudflare` check shows as could not run. Cloudflare records only deployments that happened, so a failed deploy is not visible here; a failed deploy workflow is already the `ci-red` finding.

  **Site down.** A site whose previous ring slot is `0` and whose probe this pass is down too, two failed probes in a row, is a finding (`site-down-<namespace>`, owned by the probes).

  **Error rate.** A Worker that errored on more than 1 percent of at least 100 requests in the most recent complete hour is a finding (`site-errors-<namespace>`, owned by the `cloudflare` check, so it clears only on a pass where Cloudflare was read in full).

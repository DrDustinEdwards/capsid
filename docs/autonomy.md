# Autonomy

What the machine does with no human in the loop. Capsid runs no job queue and no merge loop: project threads do the work, and the watcher only records what it finds. A pull request merges on green, by the project thread that opened it or by GitHub's native auto-merge, with a required Reviewer check.

## The watcher

A half-hourly step on the five-minute tick that records what needs a person in `watcher_findings`, where the Portal shows it. It posts nothing and fixes nothing, and a healthy surface records nothing.

- **What it reads.** `/health` against master (degraded store, a deployed sha that is not master head, a backup older than the window or never run, a live schema behind the newest migration); CI on each roster repo's default branch, red for more than two hours; the Amazon backup copy ([backups.md](backups.md)); and the live checks ([live-checks.md](live-checks.md)), which read what `capsid/policy/live-checks.md` names and do not run without it.
- **Every finding has a class.** `findingClass` in `src/watcher-checks.ts` assigns one beside `OWNERS`, and `test/watcher-classes.test.ts` fails when the tables disagree. **alert**: site down, error rate, deploy rolled back or rollback failed, stale or never-run backup and the Amazon copy findings, domain expiry, CI red over two hours, schema behind, degraded health, deploy drift, site map drift, unmapped repos, an invalid live-checks config, an unhealthy site after self-repair. **digest**: CSP, security headers, analytics, other `live-*` findings, `site-weekly-*` and stale canon. **attention**: agent anomalies and a late Amazon copy. The class decides where the Portal shows a finding. The weekly digest per site is the open digest-class rows grouped by namespace; the daily email adds it on Mondays UTC ([portal.md](portal.md), "Daily digest").
- **Agents out of pattern** (`src/anomaly.ts`). Each pass counts audit rows for minted agents (not the watcher) per actor, action and hour and compares the last 24 hours with the 14 days before. A finding when an agent writes an action it never wrote in its baseline (`anomaly-new-action-<agent>-<action>`); when its busiest hour is over three times its busiest baseline hour and at least 30 rows (`anomaly-rate-<agent>`); or when an agent with no baseline is first used between 00:00 and 06:00 Chicago time (`anomaly-first-use-<agent>`). It suspends and revokes nothing. A hit clears when it leaves the 24-hour window. Actions that write no audit row (most reads) are not seen.
- **Domain registrations** (`src/domain-expiry.ts`). The registrable domain of each configured site is read by RDAP (the IANA bootstrap kept a week in KV, each domain's `expiration` kept a day). A finding 30 days before expiry (`domain-expiry-30d-<domain>`) and another 7 days before (`domain-expiry-7d-<domain>`). A domain that could not be read is logged (`WATCHER_DOMAIN_UNREAD`) and the check does not count as run, so a failed read never clears an open finding.
- **Stale canon after a merge** (`src/stale-canon.ts`). Each pass lists every mapped namespace's newest closed pull requests (primary repo, 20 per list, at most 20 namespaces) and reads the files of up to 5 new merges into the default branch, kept in `APP_KV` as `stale-canon:merges` for 30 days. A canon document (a path in `src/canon.ts`, or type core, spec, protocol, procedural or reference; never under `archive/`, `research/`, `reports/` or `audits/`, never superseded or closed) is flagged when it cites a file a merge deleted or renamed, by path in its body or a typed edge, or has an edge to a file a merge modified. One digest finding per document and pull request (`stale-canon-<namespace>-<pr>-<tag>`). Nothing is rewritten. A document written after the merge is not flagged, so rewriting it, dropping the citation, or the merge leaving the window clears the finding. A description in words with no path is not caught.
- **Deploys** (`src/deploy-outcomes.ts`, table `deploy_outcomes`). For each repo in `DEPLOY_ROSTER` the watcher reads the newest three completed push runs on the default branch. A run whose job is named "live gate" (or "<caller job> / live gate" when the gate runs in a called workflow such as devkit's `worker-deploy.yml`) is recorded once as `verified`, `rolled_back` (with where production went), `rollback_failed`, `rollback_skipped` (the guard declined) or `unverified` (the gate failed with no rollback), with the pull request GitHub links to the commit and, for a rollback, `restore_seconds` (the end of the gate's own deploy job to the end of the rollback step). GitHub serves no step summary through its API, so the outcome comes from the job's conclusion, the rollback step's conclusion and its check-run annotations. A known run is read from D1. The newest recorded deploy raises a finding when it was rolled back (`deploy-rolled-back-<namespace>`) or its rollback did not take effect (`deploy-rollback-failed-<namespace>`); a later verified deploy clears it. The check counts as run only when every repo was read.
- **Finding memory.** One row per fingerprint in `watcher_findings` (`src/watcher-findings.ts`), so a condition seen every pass is one finding. **open**: each pass that sees it adds one to `seen_count`, sets `last_seen_at` and appends the evidence, keeping the newest 20 sightings. **cleared**: its owning check ran and did not see it; `cleared_at` is set and `reopen_after` is six hours later (`REOPEN_QUIET_MS`). Seen again inside that quiet period it is counted and left cleared; after it, the row opens again. A finding with no row is inserted open. Every write is keyed on the fingerprint and a state move is guarded on the state it was read in, so the tick and the Portal's Refresh cannot both move a row; a lost move is logged as `WATCHER_FINDING_MOVED`.
- **CI red is one incident per namespace**: the fingerprint is `ci-red-<namespace>` and each sighting's head sha is evidence.
- **Cadence** is 30 minutes, on the five-minute tick. It spends no model tokens and no CI minutes.

### The snapshot

Each pass is kept in `ops:snapshot` (`APP_KV`, `src/ops-snapshot.ts`), which the Portal reads. It holds:

- every check as clear, finding or could not run;
- `/health`;
- the Amazon copy's report;
- each roster repo's latest CI run;
- the site configuration compared with the registered namespaces;
- a probe of every configured site (`ops_sites`), and none when nothing is configured;
- Cloudflare's view of each site: its last ten deploys and 24 hourly buckets of requests and errors.

The snapshot is written before `watcher:last`, so one that cannot be written fails the pass and the next tick runs it again.

**Probes.** Each site's health route is read, or its root where it has none, and the root as well when the health route fails, so a broken health route on a site that is up reads as degraded, not down. Capsid itself is read in-process. Each site keeps a 7-day ring of half-hour slots; a slot no pass reached is no data, never up.

**Reading it over MCP.** `capsid_admin_read_ops` action `snapshot` (admin only) returns the snapshot whole, one site's entry with `site`, or one slot of its ring with `site` and `slot` (0 the newest, up to 335) or `at`. A slot reads `up`, `down`, `no-pass` or `outside-ring`. No snapshot yet, or one that does not parse, is a named error.

**Cloudflare** (`src/ops-cloudflare.ts`) is read once per pass with `CF_OPS_TOKEN` ([portal.md](portal.md), "The Cloudflare token"); the account is `CF_ACCOUNT_ID`, or `R2_ACCOUNT_ID` where that is unset. A script is named in the map only where the host proves it (a `workers.dev` host's first label); any other site is resolved from the account's Workers custom domains, and one that resolves to nothing is unresolved, never guessed. Deploys come from the script's deployments list and errors from one GraphQL Analytics query (`workersInvocationsAdaptive`). A failed query is no data with its reason, never zeros. With no token nothing is fetched and the `cloudflare` check could not run. A failed deploy is not visible here, because Cloudflare records only deployments that happened; the failed workflow is the `ci-red` finding.

**Site down.** A site whose previous ring slot is `0` and whose probe this pass is down too is a finding (`site-down-<namespace>`).

**Error rate.** A Worker that errored on more than 1 percent of at least 100 requests in the most recent complete hour is a finding (`site-errors-<namespace>`, owned by the `cloudflare` check, so it clears only on a pass where Cloudflare was read in full).

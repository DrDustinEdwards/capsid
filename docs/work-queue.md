# The work queue

The queue hands a task from a chat that has no shell to a session that has no conversation. A job is a title plus a body, and the body is the full prompt a driver executes. `jobs` carries the lifecycle: `post`, `claim`, `heartbeat`, then `complete`, `fail`, `block` or `resume`. `supersede` closes a job the seat replaced before any work was done on it. The seat merges. Drivers never hold `can_merge`.

- **Bodies are signed**, with the same key and envelope as the loop's task documents. `claim` verifies the body first. A job edited after signing is marked failed, not left queued. A job is executable input arriving as a database row. The driver is a session holding local shell and repo credentials.
- **Leases, not locks.** A claim runs four hours. A five-minute tick returns an expired one to the queue. One claim per caller across every namespace.
- **A job can require flags.** `post` takes `required_flags`, stored in `jobs.required_scopes`. A claim by an agent lacking them is refused and the job stays queued.
- **Blocked is a pause.** A job reaching a push, a deploy, a secret, a live migration or a merge stops and is blocked with the exact command a human must run. Blocked jobs surface in `improve_status` with that command, with how many gates the job hit and how many times it came back. `resume` then returns it with a fresh lease to the driver that blocked it, records what was approved, and re-verifies the signature. When that driver already holds another claim, or the job was blocked by a shared identity (the admin identity every chat tab connects as, or a legacy operator key) rather than one driver's `agent:` credential, resume puts the job back in the queue instead, with the approval attached, and the next free session claims it. The audit row says `returned_to: "queued"` and names the previous holder. What was approved reaches the next holder as `resume_note`: `claim`, `heartbeat` and `list` for one named id return the latest resume's reason, who gave it and when, and the job's mirrored document carries the same line for `brief`. An approval longer than one line (rulings, an ordered plan) goes in resume's optional `note`, which is handed on in full the same way: as `resume_note.note`, and as its own block in the mirrored document. Until 2026-09-24 the reason lived only in the audit row, which no driver can read, and two dustinedwards drivers had to ask the seat again. `claimed_at` is left alone, so a job's duration runs from its first claim. The seat that approves is routinely not the session that blocked, so any caller may resume, except the job's own claimant: the driver that blocked a job cannot resume it with a plain resume, with or without `take`, unless it is the admin or holds `can_merge`, because a driver cannot approve its own gate. It may still resume through `approved_by_policy` for a branch push or a pull request (see `docs/autonomy.md`). A caller that passes `take` holds the job itself instead, and that resume asks the same questions a claim asks: the job's `required_flags` and `min_record` are checked against the caller. A job at the correction cap is refused for everyone but an admin.
- **A job can require a track record.** `post` also takes `min_record` (`{prs_merged: n}`), stored in `jobs.min_record`. `required_flags` asks what a driver is permitted to do. This asks what it has already done, measured against the same agent record the console shows. A claim below the bar is refused and the job stays queued.
- **`complete` takes a `result_ref`**, a document key or a pull request URL, and an optional `evidence` object (`prs`, `commits`, `files_changed`, `tests_added`).
- **Finishing a job writes one row of evidence.** `complete` and `fail` each write a single `job_outcomes` row. The Worker never stores a count it could check and did not: every pull request named in `evidence` is read from GitHub, so the merge, commit and file counts recorded are GitHub's rather than the driver's, and the last one's head commit is checked for a CI conclusion. A per-field `verified` flag says which numbers were checked. A field nobody reported is `NULL` rather than `0`. The row is written once, enforced by its primary key. An unreachable GitHub costs the verified flags, never the driver's ability to close finished work. When only some of the named pull requests can be read (one in a repo the namespace does not map, say), the Worker keeps what it read: `prs_merged` counts the ones read and is verified, CI comes from the last named one if it was read, and each read pull request's merge state is written to its `job_outcome_prs` row. `prs_opened`, commits and files stay the driver's and unverified, so the merged count is never taken for a total, and the run is neither a win nor a loss for skill credit. The daily sweep retries an unread pull request for 30 days; one outside the namespace's mapping stays unread.
- **The seat can step in on a claim whose holder is gone.** `release` returns a claimed job held by another credential to the queue, with a reason recorded in a `job-released` audit row, and writes no `job_outcomes` row: the job is worked again and ends with a real outcome. It keeps `claimed_at`, so the job's duration runs from its first claim. `fail` on a job somebody else holds fails it for the seat and writes the holder's outcome row (`job-admin-fail`). Both are for the admin or a `can_merge` caller. There is no seat `complete`: the seat did not do the work, so a job whose work landed is released and the next session completes it with the pull request as evidence, which the Worker verifies.
- **A replaced job is superseded, not failed.** When the seat reposts a corrected body, reorders the queue or withdraws a job before any work starts, it calls `supersede` with the job id, a reason and, when there is one, `replaced_by`, the id of the job that replaces it in the same namespace. The job ends with status `superseded` and the summary `Superseded by <id>: <reason>` or `Superseded: <reason>`. A queued job may be superseded by any caller that may write its namespace. A claimed job may be superseded only while it records no work (no gate hit, no resume, no correction, no `result_ref`), and only by its holder or the seat (admin or `can_merge`); anything later is failed. It writes no `job_outcomes` row, so it counts in no failure count, agent record or skill score. Before `migrations/0020_jobs_superseded.sql` the seat claimed and failed such jobs; that migration relabelled the failed ones whose summary begins `Seat repost`, `Seat withdrawal`, `Seat reorder`, `Seat hold` or `Superseded`.
- **Agent records are built from those rows.** `improve_status` and the console carry a record per credential: jobs done, failed and blocked, gates hit and resumes, pull requests opened and merged, a merge rate, a CI green rate and a median duration. Counts and rates only. Never a composite score. Only a verified field feeds a rate. A rate built from what a credential said about itself is that credential scoring its own work. A rate with no denominator is `null`, not zero.
- **Two corrections, then a human.** `resume` makes a gate a pause rather than an ending. `corrections_count` bounds the loop that opens: a driver sent back for correction twice has spent the budget, and the third hand-off is refused for a driver and for the seat, with `retry cap; human decision required` written into the summary above whatever the driver said. Only an admin resume passes at the cap, and it does not spend the budget. The human arriving lifts the cap. Only a CHANGES review or a `resume` passing `correction` spends from it; a plain resume after a gate spends nothing (ruled 2026-09-16, after three ordinary pushes put job_466d6472511e at the cap). The counter is separate from `blocked_count` and `resumed_count`, which are history and count every gate a job legitimately passed.
- **A reviewer, when a job asks for one.** `post` takes `review_required`. The driver then cannot complete, block or fail a job carrying a pull request until a comment on it starts with `REVIEW:` and ends with `APPROVE`, `CHANGES` or `BLOCK`. An `APPROVE` must also quote the pull request's current head sha, full or as a prefix of at least 7 hex characters (`REVIEW: checked abc1234, reads right. APPROVE`); one that quotes no sha or an older head does not count, so a push after the approval needs a fresh review. APPROVE hands it on as it would with no reviewer. CHANGES sends it back to the driver and spends a correction. BLOCK stops it for the seat with the objection as the reason. The newest review wins: a reviewer that watched a fix land may change its mind. The mark is a comment, not a GitHub review approval, because the reviewer holds `can_comment_pr` and nothing else. All three transitions consult it. A gate on one is a gate the others would skip, and `fail` consulted nothing at all until 2026-09-13, so a driver holding a `CHANGES` it did not want could close the job as failed and leave the pull request for the seat to find.

**`complete` must name a pull request**, in `result_ref` or in `evidence.prs`. Before 2026-09-13 a job whose `result_ref` was not a pull request URL proceeded, and `result_ref` is chosen by the driver, so the party being reviewed decided whether it was reviewed. `block` and `fail` still work with no pull request, because a job stopped at a gate has usually opened nothing and work that could not be done has none.

**A verdict counts only from a comment Capsid posted for an actor holding `can_comment_pr`.** The author login cannot answer this, since every comment Capsid writes is authored by the same App installation; what answers it is who asked Capsid to post, which `audit_log` already records beside the comment id. A driver with local `gh` can still write the envelope, and it is no longer a review. That mattered more than it looks: the newest verdict wins, so such a comment also overwrote a real `CHANGES`.

An unreadable GitHub holds the job rather than reading as an approval.
- **The table is the source of truth for status.** Every job mirrors to `<namespace>/jobs/<id>.md`, rewritten in the same batch as each transition, so `brief` and `search` see the queue. Every transition is a keyed `UPDATE ... RETURNING`, so one caller wins a contested job.

The driver is the `/improve work` command in Claude Code: it resumes a cleared gate, claims one job, does it in that namespace's clone under that repo's rules, and reports back.

**One driver session per project folder.** The bearer token is fixed when the MCP server is configured, so a session holds one credential and works one namespace. Each repo folder configures its own from `~/.capsid/agent-<ns>-driver.key`. `/improve work all` therefore does not walk the portfolio on one credential: it names the repo folders and stops, and each is launched separately. It could not do more if it wanted to, because a namespace-scoped agent that names no namespace on `jobs` is refused.

# The work queue

The queue hands a task from a chat that has no shell to a session that has no conversation. A job is a title plus a body, and the body is the full prompt a driver executes. `capsid_work_jobs` carries the lifecycle: `post`, `claim`, then `complete`, `fail`, `block` or `resume`. `supersede` closes a job the seat replaced before any work was done on it, `edit` corrects one nobody is working, `record` writes the outcome of work done on a queued job nobody claimed, and `begin` marks a queued job started. `fire` starts a cloud session for a queued job through its namespace's routine (docs/routines.md). The old `start` action, which dispatched a GitHub Actions session, is retired. A job can also be worked with no claim at all: the pull request is the claim, and `complete` naming it closes the queued job. A PR not auto-merged is merged on green by its session or the seat. Drivers never hold `can_merge`.

- **Bodies are signed**, with the same key and envelope as the loop's task documents. `claim` verifies the body first. A body changed after signing by anything other than `edit` (which signs again) is marked failed, not left queued. A job is executable input arriving as a database row. The driver is a session holding local shell and repo credentials.
- **A claim has no lease and no limit** (job_2c92174d5bff, 2026-10-11). `claim` makes the caller the job's holder and the claim never expires: there is no four-hour lease, no heartbeat and no sweep that returns a claim to the queue. A caller may hold any number of jobs, on any repo, and every holder action names the job it acts on. A holder that is gone is released by the seat (`release`, below). Migration 0044 turned every job that was still claimed into a queued job marked started by its holder. `jobs.lease_expires` stays as a column nothing reads or writes, and an `agents.scopes` JSON that still carries `max_claims` has it ignored.
- **Two sessions on one key are told apart only by the job id each names.** A bearer key names a credential, not a session, so two tabs configured with the same driver key are the same caller to Capsid. Every holder action (`complete`, `fail`, `block`) names its job id and acts on that job only, so a session cannot touch the other's job by accident; it can by naming the other's id, and the queue cannot tell. The hook and telemetry receivers bind a driver key to a job only while it holds exactly one (docs/hooks.md, docs/telemetry.md), so while a driver holds two, its sessions' telemetry is recorded against no job. A per-claim session token (minted at `claim`, required on each holder action) would close that; it needs a column and a new argument on every holder action, so it is recommended, not built.
- **Capsid picks the model.** Nobody names a model (Dustin, 2026-10-03). `post` assigns the job's `kind` and the model and effort Capsid recommends, in the Worker (`src/model-routing.ts`, migration 0032); `kind` is optional on `post` and is read from the poster and the title when absent (a watcher finding, a title starting `Design` or `Build`, a security surface, routine maintenance, docs, a mechanical edit, else `other`). The rules are data in that file (`ROUTING_RULES`, `ROUTING_RULES_VERSION`): high risk to Opus at high effort, design and security to Opus, builds to `opusplan` (Opus plans, Sonnet executes), watcher findings and maintenance to Sonnet, docs to Sonnet at low effort, mechanical edits to Haiku, anything else to `opusplan`. Trial arms (`TRIAL_ARMS`, rules version 2, 2026-10-10) send 25 percent of routine watcher, maintenance and docs jobs to Haiku (Claude Haiku 5.5, `claude-haiku-5-5`) at the rule's effort, chosen by a stable hash of the job id so post and claim agree; a risky job, or one that names its model, never takes an arm, and the claim's `routing.trial` names the arm's model or is null. An arm switches no kind: the kind's rule still names its model. Risk before a pull request exists is what the job says about itself: a payments namespace (foxhound), a blast-radius flag in `required_flags` (`can_merge`, `can_direct_write`, `can_dispatch`, `can_write_workflows`, `can_touch_protected`, `money_paths`) or `gate_required`. A job whose body has a line `model: <alias>` is routed there, except that a high-risk job is never routed below the high-risk rule's model. `claim` settles the model again (a job posted before routing is routed then) and, for a job that already carries a pull request, reads every page of that PR's files with `riskOf`, which counts the money paths and auto-merge's refused paths, deletions, removed files and backup or restore paths, and can only raise the risk; a PR whose files cannot be read whole is said in `routing_note` and routed as high risk, never taken as routine. The claim returns `routing`: model, effort, kind, risk, reason and how to follow it (a scheduled or cloud launch passes `--model`; an interactive driver does the work in a subagent on that model and keeps its own session for coordination). Every outcome records `job_kind`, `model_chosen` and `model_actual` (the `versions.model_id` the session reported). `capsid_work_jobs` action `list` with `view` `models` is the learning table: per kind and the model Capsid chose (an outcome whose session reports another model is left out, never moved, since `model_actual` is the session's own word), the share merged with green CI, corrections and cost, only for cells with at least 10 outcomes, and the rule changes the evidence supports (a cheaper model that did as well; a stronger one when the current is under 60 percent), plus `trials`: each arm against its kind's rule, `collecting` until both cells hold 10 outcomes, then `supports` (the same change `proposals` names) or `does not support`, with merged-green counts and mean cost (test/model-routing.test.ts). It applies none: the seat approves each rule edit. It reads every namespace's outcomes, so only a caller scoped to every namespace may.
- **A job can require flags.** `post` takes `required_flags`, stored in `jobs.required_scopes`. A claim by an agent lacking them is refused and the job stays queued.
- **A block can be a question** (Track A D4, 2026-10-07). `block` with `question: true` is for a session that needs an answer, not a command run: the reason is the question, the Worker fixes the command as "Answer in a resume note" (a command sent with it is refused), and the summary starts with `QUESTION: `, which is how `capsid_run_improve` action `status` (`blocked_jobs[].question`) and the Portal feed (`question` on the job) tell it from a gate. No new status and no migration. The seat answers with `resume` and a note, and every later `claim` and `list` for the job returns it in `resume_notes`, so the question is not asked twice. The Portal's Queue marks it Question and says what it asks, and its drawer shows the question in place of a command, with Answer for Resume (docs/portal.md).
- **Overlap warnings** (Track A D1, 2026-10-07). `block` and `complete` that name a pull request of the namespace's repo (the job's `result_ref`, `evidence.prs`, or a pull request URL in the block command) read that pull request's files and the files of every other open pull request there, from GitHub (`src/github/pr-files.ts`, the one reader the auto-merge tick also uses; a rename counts under both names). Where two share a file the summary gains one line, `Overlaps: #134 with #130 (src/jobs.ts). Merge in PR order, oldest first, and rebase the later.` (before the resume marker on a block, so the command is still last), the response carries `overlaps`, and the audit row records it. Nothing is predicted or declared at post, and the warning never refuses a call. A read that fails, or more than 20 other open pull requests, is said in the line (`Overlaps: not checked (...)`), never left to read as clean. A call that names no pull request of the repo reads nothing from GitHub. Tests: test/job-overlaps.test.ts, test-integration/job-overlaps.test.ts.
- **Blocked is a pause.** A job reaching a push, a deploy, a secret, a live migration or a merge stops and is blocked with the exact command a human must run. Blocked jobs surface in `capsid_run_improve` action `status` with that command, with how many gates the job hit and how many times it came back. `resume` then returns it to claimed for the driver that blocked it, records what was approved, and re-verifies the signature. When the job was blocked by a shared identity (the admin identity every chat tab connects as, or a legacy operator key) rather than one driver's `agent:` credential, resume puts the job back in the queue instead, with the approval attached, and the next free session claims it. The audit row says `returned_to: "queued"` and names the previous holder. What was approved reaches the next holder as `resume_note`: `claim` and `list` for one named id return the latest resume's reason, who gave it and when, and the job's mirrored document carries the same line for `capsid_start_session`. They also return `resume_notes`, every resume note for the job, newest first (the first is `resume_note`), each with its own signature check, so an approval given at one resume is still there after the next (job_5765103c658f was resumed 15 times and its early notes carried the PR order and rulings). The notes are capped at 64 KB together: the oldest are left out and counted in `resume_notes_dropped`, and the newest is always returned. A note whose signature does not match is withheld in place and does not fail the claim; only the newest note's mismatch fails it, as before. The mirrored document lists the earlier resumes under an "Earlier resumes" heading. An approval longer than one line (rulings, an ordered plan) goes in resume's optional `note`, which is handed on in full the same way: as `resume_note.note`, and as its own block in the mirrored document. Until 2026-09-24 the reason lived only in the audit row, which no driver can read, and two dustinedwards drivers had to ask the seat again. `claimed_at` is left alone, so a job's duration runs from its first claim. The seat that approves is routinely not the session that blocked, so the resumer need not be the claimant, but a plain resume, with or without `take`, is the seat's act: only the admin or a `can_merge` caller may make one. A driver cannot approve a gate, its own or another driver's in the same namespace (Grok audit 2026-10, S1: a sibling driver with the write grant could otherwise clear a deploy, secret or force-push gate). The driver that blocked a job may still resume it through `approved_by_policy` for a branch push or a pull request (see `docs/autonomy.md`). A caller that passes `take` holds the job itself instead, and that resume asks the same questions a claim asks: the job's `required_flags` and `min_record` are checked against the caller. A job at the correction cap is refused for everyone but an admin.
- **A manual step is done when Capsid can see it** (improvement list item 14). A step only Dustin can take (an npm publish to approve, an Access app, a secret, a repo's About box) is a block like any other: the reason carries the click steps, one per line, and a line `check: <form>` in the reason or the command names the result that proves it done. The forms: `check: secret NAME on <namespace>` (the site's Worker lists the secret, from the names the watcher stores for a site whose row expects secrets, src/secret-presence.ts); `check: npm <package>@<version>` (registry.npmjs.org lists that version); `check: access app <name>` (Cloudflare Access has an application of that name, case aside; CF_OPS_TOKEN needs Access: Apps and Policies Read); `check: github about <owner/repo>`, optionally followed by `homepage <url>` (the repo, one its namespace maps, has a description and a homepage, that homepage when named, read through the App). The watcher's pass reads them for the oldest 25 blocked jobs naming one, up to 5 steps each, and writes seen, unseen and unread counts per job to `stale:steps` in APP_KV (src/manual-steps.ts). A job whose every step was seen after it last changed is settled as a merged pull request settles one: the inbox stops counting it as waiting on Dustin, and the stale view lists it as `steps-seen` so it is closed or resumed. A failed read, a line in no known form, or a secret not read since the job blocked is unread, never seen. Nothing moves the job. Tests: test/manual-steps.test.ts.
- **A namespace that keeps failing stops handing out work.** When the jobs of one namespace were failed by their own holders three times in 24 hours, `claim` refuses every job in it, which stays queued, until the seat or Dustin resets the breaker (`capsid_admin_control_improve` action `breaker_reset`, admin only, or Reset breaker in the Portal's Settings, Automation and namespaces section). The count is read from the audit log at each claim (`src/job-breaker.ts`), so there is no stored flag to drift: a reset records the time, and only failures after it count. A seat's admin fail and a claim that fails a tampered body are not the drivers failing, and do not count. `breaker_reset` also takes `threshold` (1 to 50) for every namespace. `capsid_run_improve` action `status` reports each namespace's breaker, and the watcher files an open one (OWASP ASI08, job_9e602b31888f). Two kinds of holder fail are left out of the count, each shown by something other than the driver's word (`src/fail-exemption.ts`): one Capsid's own complete would refuse right now on the pull request the job is bound to (red or unfinished CI, a test taken away), and one whose reason has a line `REMAINING: 2, 4` naming some but not all DONE WHEN items, where at least one item not named says it changes a path and the bound pull request changes every such path. The fail's audit row carries `breaker_exempt` (`machinery` or `remainder`).
- **Resume notes and block commands are signed** (OWASP ASI07, job_9e602b31888f). A job body is signed at `post`; what a job carries afterwards is now signed too, with the same key, bound to the job id and to what kind of text it is (`src/job-signing.ts`). A resume signs its reason, note and caller into the audit row, and every reader checks it: `claim` and `list` for one id and the mirrored document return `resume_note.signature`. A note whose signature does not match is withheld (its reason replaced, its note dropped), and `claim` fails the job rather than handing it out, as it does a body that fails its check. `complete`, `fail` and `block` sign `result_summary` into `jobs.summary_sig` (migration 0027); every other writer of the summary clears it. `capsid_run_improve` action `status` and the Portal feed report a blocked job's `command_signature` and withhold a command that does not match. A note or summary written before signing carries no signature and is served labelled `legacy-unsigned`, never as verified.
- **The mirror is the jobs code's alone** (Grok audit 2026-10, M2). A job's mirrored document, `jobs/<id>.md` in its namespace, is written only by `capsid_work_jobs`, in the same batch as the row. `capsid_write_doc` actions `write`, `restore` and `move` and `capsid_delete_doc` refuse any path under `jobs/`, for every caller and flag, because `capsid_start_session` serves a task document from there and one written by hand could stand in for a signed job nobody posted. Tests: test/docs-guards.test.ts.
- **A job can require a track record.** `post` also takes `min_record` (`{prs_merged: n}`), stored in `jobs.min_record`. `required_flags` asks what a driver is permitted to do. This asks what it has already done, measured against the same agent record Capsid Portal shows. A claim below the bar is refused and the job stays queued.
- **`complete` takes a `result_ref`**, a document key or a pull request URL, and an optional `evidence` object (`prs`, `commits`, `files_changed`, `tests_added`).
- **CI on complete** (Grok design review, 2026-10-23). `complete` is refused unless every pull request it names (`result_ref`, `evidence.prs`), and the one the job is bound to, shows CI that ran and passed on its head (`src/complete-ci.ts`). Green is the only pass. A check still running is a wait: the job stays claimed and nothing is written. A failed check is red. A head where no check passed (none ran, or every one was skipped or neutral) is not green when the pull request changes any file that is not docs. GitHub unreadable is a wait too. A pull request that takes a test away is refused as well, since green CI shows nothing once the test that would fail is gone (`src/test-protection.ts`): it removes a test file, removes or renames a test (a JS `it`, `test` or `describe`, a Python `def test_` or `class Test`, a Go `func Test`), or adds a skip (`.skip`, `xit`, `@pytest.mark.skip`, `t.Skip` and the like), unless the job body names that file or test. Editing a test's body is left to the reviewer and to auto-merge. The poster numbers the items under DONE WHEN (at most 10; `post` and `edit` warn past that), and an item that says it changes a path in backticks ("1. The breaker skips run keys: changes `src/job-breaker.ts`"; a path ending in `/` is a directory) is checked here: a pull request the complete names must change that path (`src/job-checklist.ts`). Every other item is the session's to meet and the reviewer's to read. A job whose body has a line `TEST ON BASE` asks for its tests to be run on the base: its session labels the pull request `test-on-base`, and `.github/workflows/test-on-base.yml` (this repository only) lays the pull request's test changes alone on the base and runs its test files there and on the head (`scripts/test-on-base.mjs`). At least one test must fail on the base and every one that did must pass on the head; a test file that does not load on the base is not counted. `complete` then needs that `test-on-base` check run to have passed. The first refused holder's complete binds the job to that pull request in `result_ref` (`job-ci-bound`), so naming another next time does not escape it. The seat's close and a complete without a claim are gated the same way and bind nothing, since they write nothing before they are allowed. A pull request Capsid cannot read (no GitHub App, or a repo the namespace does not map) is not gated. What this does not catch: a weak test, a skipped requirement, a misread job.
- **Finishing a job writes one row of evidence.** `complete` and `fail` each write a single `job_outcomes` row. The Worker never stores a count it could check and did not: every pull request named in `evidence.prs`, and the job's `result_ref` when it is a pull request URL, is read from GitHub whoever completes the job (the seat closing a job it took sends only `result_ref`), so the merge, commit and file counts recorded are GitHub's rather than the driver's, and the last one's head commit is checked for a CI conclusion. A per-field `verified` flag says which numbers were checked. A field nobody reported is `NULL` rather than `0`. The row is written once, enforced by its primary key. An unreachable GitHub costs the verified flags, never the driver's ability to close finished work. When only some of the named pull requests can be read (one in a repo the namespace does not map, say), the Worker keeps what it read: `prs_merged` counts the ones read and is verified, CI comes from the last named one if it was read, and each read pull request's merge state is written to its `job_outcome_prs` row. `prs_opened`, commits and files stay the driver's and unverified, so the merged count is never taken for a total. The daily sweep retries an unread pull request for 30 days; one outside the namespace's mapping stays unread. The sweep also reads GitHub for an outcome recorded before `result_ref` was read (job_d5262df1dc32), one whose `commits` are still unverified and whose `result_ref` is a pull request: when every pull request it names can be read it writes GitHub's counts and CI, and an `outcome-backfilled` audit row, actor `system:outcome-backfill`, holds the values before and after. `tests_added` is never touched. Each row pins the pull request it named, by GitHub's node id and when it was opened, on its first read, because a URL names a number and a recreated or transferred repository hands numbers out again. A later read that finds a different pull request at that number marks the row `unverifiable` (`identity-changed`) with a note, and the row leaves the sweep and every count for good. A row recorded before the id was kept is pinned on its next read, unless its repository was created after the outcome named the pull request (`repo-recreated`) or the pull request answering was opened after it; a read that cannot decide leaves the row as it was (`src/outcome-prs.ts`, `migrations/0026_outcome_pr_identity.sql`).
- **The seat can step in on a claim whose holder is gone.** `release` returns a claimed job held by another credential to the queue (a claim never expires, so this is the only way a dead holder's claim ends), with a reason recorded in a `job-released` audit row, and writes no `job_outcomes` row: the job is worked again and ends with a real outcome. It keeps `claimed_at`, so the job's duration runs from its first claim. `fail` on a job somebody else holds fails it for the seat and writes the holder's outcome row (`job-admin-fail`). `complete` on a BLOCKED job somebody else holds completes it for the seat (`job-admin-complete`): the job stays held by the driver that did the work, so the outcome row credits that driver, and the pull request in `result_ref` or `evidence.prs` is verified against GitHub as for a holder's complete. The audit row names the seat as actor and the holder in `held_by`; the seat's `claim`, if it sends one, is recorded under the seat. A queued job is not the seat's close: it is completed without a claim, below. The seat's close refuses a claimed job (its holder completes it, or the seat releases it first) and a finished one, and a `review_required` job without an APPROVE on the pull request's head: the seat's close writes nothing until the review allows it, so a CHANGES or BLOCK is answered rather than escaped. Resume with `take` then `complete` still makes the seat the holder, and credits the seat. All three are for the admin or a `can_merge` caller. The seat's close writes one `job_touches` row of kind `admin_complete` (migration 0031) in the same batch: the seat as actor, `waited_ms` from the job's latest gate, and the holder and `result_ref` in `detail`. The Portal's and the `capsid_admin_run_controls` tool's `close_shipped` control is this same close (stale jobs D4, ruled 2026-10-09: the existing path, crediting the holder): it takes a reason, which becomes the summary "Closed as shipped by <seat>: <reason>", and passes the pull requests the job names (from `result_ref` and its summary, at most 10) as `result_ref` and `evidence.prs`, so the outcome verifies them against GitHub. `record` is the same for a QUEUED job: work was done on it without a claim, and the seat records the outcome, with the same checks, GitHub verification, records and review gate as a complete (`recordAsCaller` in src/jobs-seat.ts). It is the seat's alone, the admin or a `can_merge` caller, for closing work somebody else did; a session closing its own work completes the job with its pull request, below.
- **The pull request is the claim** (job_e68de044f8a4; Dustin, 2026-10-10, plan step 2). Cloud sessions all sign in as the admin login, which may hold one claim, so they work jobs without claiming them, the way Copilot, Codex and Claude Code Projects work a task: one branch and one pull request. `complete` on a QUEUED job nobody holds, from any caller holding the write grant on its namespace, closes it when it names the job's pull request (a pull request URL in `result_ref` or `evidence.prs`, every one on a repo mapped to the namespace, and at least one whose description names the job id); without one it is refused and nothing is written. What a claim would have asked is asked here: the job's `required_flags` and `min_record`. It runs the record path (`completeUnclaimed` in src/jobs-seat.ts), audited as `job-complete-unclaimed`: the same review gate, GitHub verification, outcome row and overlap check as a holder's complete, and the outcome credits the caller as the job's holder, so `pr_recorded_for_job` finds the pull request and auto-merge judges it like any other (policy version 7 dropped `author_is_driver`). `claim` still works for a local driver, with no lease.
- **A started label.** `begin` marks a queued job started: `started_by` and `started_at` on the row (migrations/0042), a `job-started` audit row, and a "started by" line in the mirrored document. Any caller holding write on the namespace may begin. begin verifies the body's signature as claim does, and refuses a body that does not verify, telling the session not to run it. The label never expires and refuses nothing: claim, complete and every other transition go on as before. The first begin keeps it; a second writes nothing and is told who started the job and when, and so are `claim` and `list` for one id (`started`). The Portal's Queue shows "Started by" on a queued job's row (src/jobs-begin.ts).
- **A replaced job is superseded, not failed.** When the seat reposts a corrected body, reorders the queue or withdraws a job before any work starts, it calls `supersede` with the job id, a reason and, when there is one, `replaced_by`, the id of the job that replaces it in the same namespace. The job ends with status `superseded` and the summary `Superseded by <id>: <reason>` or `Superseded: <reason>`. A queued job may be superseded by any caller that may write its namespace. A claimed job may be superseded only while it records no work (no gate hit, no resume, no correction, no `result_ref`), and only by its holder or the seat (admin or `can_merge`); anything later is failed. It writes no `job_outcomes` row, so it counts in no failure count or agent record. Before `migrations/0020_jobs_superseded.sql` the seat claimed and failed such jobs; that migration relabelled the failed ones whose summary begins `Seat repost`, `Seat withdrawal`, `Seat reorder`, `Seat hold` or `Superseded`.
- **A job nobody is working can be edited** (Dustin, 2026-10-07). `edit` changes the `title`, `body`, `priority` or `gate_required` of a queued or blocked job. It is the seat's act (the admin or a `can_merge` caller), never a driver's, and a claimed, done, failed or superseded job is refused. A new body passes the checks `post` makes and is signed by the same code (`signedJobBody` in `src/jobs-claim.ts`), so `claim` and `resume` verify it as they verify a posted body. The version an edit replaces (who, when, the old title, body as stored, priority and `gate_required`) is copied to `job_versions` (migration 0033) in the same guarded batch as the `UPDATE`, the mirror rewrite and a `job-edited` audit row naming the fields changed. `list` for one named id returns them as `versions`, newest first, to a caller holding write, as it returns the body. A new title held by another open job in the namespace is refused, naming that job, and the unique index refuses one that races the check. An edit that changes nothing is refused. The Portal has no edit control yet.
- **A job wanted but not now can be parked** (Dustin, 2026-10-07). `park` sets a queued job aside and `unpark` returns it. Both are the seat's act (the admin or a `can_merge` caller), never a driver's. `park` needs a one-line reason of at most 300 characters saying when the job comes back, and refuses a claimed or blocked job (resume or supersede those). A parked job has status `parked`: `claim` reads only queued rows, so it is never claimed, and the overnight plan reads only queued rows, so it is never planned. It stays in `list` (status `parked`, the reason in `result_summary`) and its mirror document stays active, so it is still searchable. Parked holds no title slot (it is not in `OPEN_JOB_STATUSES`, so the unique index, the feed, namespace delete and the watcher's duplicate check are unchanged); `unpark` is therefore refused, naming the job, when another open job has taken the title. Each change writes a `job-parked` or `job-unparked` audit row. `test-integration/jobs.test.ts` ("park") holds the rules. The Portal shows parked jobs in the Queue's Parked group, and its job drawer parks and unparks through the `park_job` and `unpark_job` controls, each with Undo (docs/portal.md).
- **Agent records are built from those rows.** `capsid_run_improve` action `status` and Capsid Portal carry a record per credential: jobs done, failed and blocked, gates hit and resumes, pull requests opened and merged, a merge rate, a CI green rate and a median duration. Counts and rates only. Never a composite score. Only a verified field feeds a rate. A rate built from what a credential said about itself is that credential scoring its own work. A rate with no denominator is `null`, not zero.
- **Two corrections, then a human.** `resume` makes a gate a pause rather than an ending. `corrections_count` bounds the loop that opens: a driver sent back for correction twice has spent the budget, and the third hand-off is refused for a driver and for the seat, with `retry cap; human decision required` written into the summary above whatever the driver said. Only an admin resume passes at the cap, and it does not spend the budget. The human arriving lifts the cap. Only a CHANGES review or a `resume` passing `correction` spends from it; a plain resume after a gate spends nothing (ruled 2026-09-16, after three ordinary pushes put job_466d6472511e at the cap). The counter is separate from `blocked_count` and `resumed_count`, which are history and count every gate a job legitimately passed.
- **A reviewer, when a job asks for one.** `post` takes `review_required`. The driver then cannot complete, block or fail a job carrying a pull request until a comment on it starts with `REVIEW:` and ends with `APPROVE`, `CHANGES` or `BLOCK`. An `APPROVE` must also quote the pull request's current head sha, full or as a prefix of at least 7 hex characters (`REVIEW: checked abc1234, reads right. APPROVE`); one that quotes no sha or an older head does not count, so a push after the approval needs a fresh review. APPROVE hands it on as it would with no reviewer. CHANGES sends it back to the driver and spends a correction. BLOCK stops it for the seat with the objection as the reason. The newest review wins: a reviewer that watched a fix land may change its mind. The mark is a comment, not a GitHub review approval, because the reviewer holds `can_comment_pr` and nothing else. All three transitions consult it. A gate on one is a gate the others would skip, and `fail` consulted nothing at all until 2026-09-13, so a driver holding a `CHANGES` it did not want could close the job as failed and leave the pull request for the seat to find.

**`complete` must name a pull request**, in `result_ref` or in `evidence.prs`. Before 2026-09-13 a job whose `result_ref` was not a pull request URL proceeded, and `result_ref` is chosen by the driver, so the party being reviewed decided whether it was reviewed. `block` and `fail` still work with no pull request, because a job stopped at a gate has usually opened nothing and work that could not be done has none.

**A verdict counts only from a comment Capsid posted for an actor holding `can_comment_pr`.** The author login cannot answer this, since every comment Capsid writes is authored by the same App installation; what answers it is who asked Capsid to post, which `audit_log` already records beside the comment id. A driver with local `gh` can still write the envelope, and it is no longer a review. That mattered more than it looks: the newest verdict wins, so such a comment also overwrote a real `CHANGES`.

An unreadable GitHub holds the job rather than reading as an approval.
- **The table is the source of truth for status.** Every job mirrors to `<namespace>/jobs/<id>.md`, rewritten in the same batch as each transition, so `capsid_start_session` and `capsid_find_docs` action `search` see the queue. Every transition is a keyed `UPDATE ... RETURNING`, so one caller wins a contested job.

The driver is the `/improve work` command in Claude Code: it resumes a cleared gate, claims one job, does it in that namespace's clone under that repo's rules, and reports back.

**One credential per project folder.** The bearer token is fixed when the MCP server is configured, so a session holds one credential and works one namespace. A second tab in the same folder uses the same key, and holds jobs of its own by naming each job id. Each repo folder configures its own from `~/.capsid/agent-<ns>-driver.key`. `/improve work all` therefore does not walk the portfolio on one credential: it names the repo folders and stops, and each is launched separately. It could not do more if it wanted to, because a namespace-scoped agent that names no namespace on `capsid_work_jobs` is refused. Outside its namespace a driver may read only the portfolio documents in capsid (the conventions, the decisions log and its volumes, the rulings and capsid's core; docs/auth.md), which `capsid_start_session` lists under `portfolio_documents`; it cannot see capsid's jobs, research or policy.


## A body a session can act on

A session that claims a job has no conversation to ask in, and a question mid-task costs 4 to 6 hours, so the body has to carry what the session needs. Write it with five headed parts:

- **GOAL**: what and why, in a sentence or two.
- **DO**: the steps, in order.
- **OUT OF SCOPE**: what the session must leave alone.
- **DONE WHEN**: the checks that say it is finished.
- **DECIDED** or **RULES**: choices already made, and the rules that bind the session.

`post` and `edit` from a caller (src/job-body-check.ts) refuse a title or body holding an unfilled placeholder: `<ID>` or `<id>`, `<...>`, `{{...}}`, `TODO:` or `TBD`. The refusal names the placeholder and its line. Text inside a code block or an external fence is exempt, so a body may quote a template. A body missing any of the five parts is accepted, and the result carries a `warnings` entry naming what is missing. A body that states, as done, that a pull request is merged, a version is tagged or a package version is published or on npm is checked at `post` and `edit` (src/job-fact-check.ts): the pull request's merge against GitHub (a `#12` in the one repo the namespace maps, or a full pull request URL of a mapped repo), the tag against the namespace's mapped repos (`v1.2.0` or `1.2.0`, and `name@1.2.0` or `name-v1.2.0` when a name is written), and the version against npm's registry (any listed version counts; `latest` need not point at it). The package is the one written as `name@1.2.0`, or a package configured in the Portal whose name matches, or the one configured package of the namespace's repos. A claim read as false is refused, naming it, its line and what Capsid read; say it as pending ("once #12 is merged") or put a quotation in a code block or an external fence. Only a claim stated as done counts: a sentence that is a question or carries a word of plan, condition, negation or report ("once", "after", "will", "not", "yet", "said", ...) is not read, nor is text in the DONE WHEN and OUT OF SCOPE parts, a block quote or double quotes. A claim that could not be checked (a read failed, the repo is not mapped, the package is unknown or ambiguous) is accepted with a `warnings` entry saying so, never refused, and "published" with no mention of npm and no known package is not read at all. One body spends at most 10 claims and 20 reads. The watcher's, the skills refresh's and the finalize step's posts, and jobs already queued, are not checked.

Rules for the session:

1. Ask every question at the start, each with a recommended default, before any work.
2. For a reversible choice, proceed on the default and note it in the pull request.
3. Block only for money, deletion, secrets or anything public-facing.

The source is "Ask or Assume?" (arXiv 2603.26233): calibrated asking recovers most of the success lost to underspecified tasks. A mid-task question here costs hours, so asking early and assuming on the reversible is the cheaper policy.

## Claims

`complete`, `fail` and `block` take an optional `claim`, an object or its JSON string, that states what the driver says it did: `prs_opened` and `prs_merged` (up to 10 URLs each), `tests` (`run`, `passed`, `failed`, `result` of `pass`, `fail`, `partial` or `not_run`), `deploy_state` (`none`, `pending`, `deployed`, `verified` or `failed`), `files_touched` (up to 500 paths), `usage` (`cost_usd`, `active_seconds` and `tokens` of `input`, `output`, `cache_read`, `cache_creation`; non-negative, finite, tokens whole numbers; this session's own total, not a running one), and `versions` (`model_id`, `client_name`, `client_version`, `permission_mode`). A string that does not parse, or a key the claim does not know, is refused rather than dropped. `usage` and `versions` are self-reported and recorded only; nothing authorizes on them.

Each of those calls that reaches its transition writes one `job_claims` row in the same batch: the arguments exactly as sent, and the claim's fields read into columns before any verification runs, so GitHub's answer never replaces the driver's. A field the driver did not state is `NULL`, never `0` or false. Without `claim.prs_opened`, `evidence.prs` stands as the opened list. A call refused before the transition writes no row, and neither does the seat failing another credential's job.

`complete` and `fail` also write `job_evaluations` rows, one per check the Worker ran (`pr_merged`, `prs_opened`, `commits`, `files_changed`, `ci_green`), each holding the claimed and verified values side by side and whether they agree. Every gate, resume, approval, correction, note, release, supersede, seat fail and acted-on review writes a `job_touches` row naming who touched the job and, where it ended a wait, how long the job waited since its gate. docs/schema.md describes the columns.

`capsid_work_jobs` action `list` also takes `view: "plan"` (the overnight plan) and `view: "digest"` (the morning digest), both read-only and described in docs/overnight.md. The plan takes gated jobs (`gate_required`) like any other and marks them `gated` (Dustin 2026-10-07): the session does the ordinary work, lists each risky step in the pull request for the seat, and moves on. It never takes a parked job.

`capsid_work_jobs` action `list` with `stale: true` is the stale view (stale jobs D5, job_24dcf08c4c00), read-only, with the read grant and the usual namespace scope: a caller scoped to one namespace names it, and `namespace` narrows it for anyone. It refuses `view`, `status` and `id`, and returns `stale`, up to 200 rows of id, namespace, title, status, updated_at, `rule` and a one-line `reason`. The rules: `unchanged`, a blocked or claimed job whose row has not changed in 3 days; `resumed-not-completed`, a job the merge-resume step (`system:merge-resume`, src/merge-resume.ts) resumed 24 hours or more ago that is still blocked, claimed or queued; `prs-settled`, a blocked job whose named pull requests are all merged or closed, with none open or unreadable. `steps-seen`, a blocked job whose every `check:` line the watcher's last pass saw done (above), from `stale:steps`. The last comes from the `stale:prs` value in APP_KV, which the merge-resume step rewrites on each five-minute tick with merged, closed, open and unread counts for every blocked job it read, dropping jobs no longer blocked, so the view makes no GitHub reads. An entry read before the job last changed is ignored. A job matching several rules is listed once, under the first of `prs-settled`, `steps-seen`, `resumed-not-completed`, `unchanged`. Nothing in the view moves or closes a job (src/stale-jobs.ts). The Portal's Queue shows the same rows over every namespace from `GET /portal/api/stale` (docs/portal.md), and its job drawer resumes one with an optional note (stale jobs D6).

The daily maintenance pass (job_549550d73d4e, src/maintenance.ts) runs on the five-minute tick once a UTC day after 11:00 and lists; it acts twice: the merged-branch prune below, which is off until the seat turns it on, and the release-tag rule below, which is on until the seat turns it off. Its list is kept in APP_KV and served by `capsid_run_improve` action `status` as each namespace's `maintenance`, one line per item with its `rule`. The job rules are `later-passed`, `shipped-elsewhere`, `followups-missing` and `auto-resumed` (test/maintenance.test.ts and test-integration/maintenance.test.ts). The pull request rules (src/maintenance-prs.ts) read every roster namespace's repo with the reads the auto-merge tick makes, the open list and each head's check runs judged by the same `ciVerdict`, and no file lists. `pr-awaiting-seat` is a driver's pull request (its body names a job), not a draft, with every check green, listed with how long it has been open. `pr-red` is a pull request whose checks have finished with at least one failure that first finished more than 48 hours ago on the current head, listed with the failed check and its failing step, read from that check's Actions job; a re-run or a new push starts the clock again. `prs-not-checked` is a repo or a pull request whose read failed, so a failed read is never a clean result. Up to 50 open pull requests are read per repo; more are listed as not checked. `maintenance_prs_read` is the number of open pull requests the pass read in that namespace, null when it read none, so an empty list can be told from an unread one. test/maintenance.test.ts guards each pull request rule: "a green driver pull request is listed with its age", "a pull request red for more than 48 hours is listed from its first failure", "the gathered list names the failing step, counts what it read" and "a GitHub read that fails is listed as not checked".

The branch rules (src/maintenance-branches.ts) read each roster namespace's repo once a day with `capsid_close_pr` action `delete_branch` merged's own plan (src/github/prune.ts): a merged branch is one whose newest pull request in the repo merged from its current tip, and the default branch, a protected branch, a branch whose newest pull request is open, and a branch with commits after its merge are never merged branches. The auto-prune ships off. Off, each merged branch is listed as `branch-merged` with a count line, and nothing is deleted. The seat turns it on with `npx wrangler kv key put --binding APP_KV --remote maintenance:prune-merged on` (any other value, or deleting the key, turns it off). On, at most 25 merged branches per repo per run are deleted, each tip re-read just before its delete; each delete writes an `audit_log` row (actor `system:maintenance`, action `maintenance-prune-branch`, with the repo, branch, sha and pull request) before the next delete, and is listed as `branch-pruned` with the `git push origin <sha>:refs/heads/<branch>` that puts it back. `branch-stale` is any other branch with no open pull request (none, one closed unmerged, or commits after the merge) whose last commit is more than 30 days old, listed with its age; up to 30 commit dates are read per repo, and the rest are listed as not checked. With the auto-prune on, such a branch is deleted instead once its last commit is 2 days old (job_9dbaf2ecfd2c; Dustin, 2026-10-14), within the same 25 per repo per run, re-read, audit-logged with `pr: null` and listed as `branch-pruned` with its put-back command, and only when every pull request list was read in full. A screenshot branch (`shots/...` or `...-shots`) is kept while an open pull request's description names it or its tip, so an open pull request's images stay; after that it is an ordinary orphan. test/maintenance.test.ts: "PLANT: with the auto-prune on, a branch under 2 days old and a screenshot branch an open pull request shows are kept" and "an orphan is not deleted when a pull request list was not read in full". The keep list is the APP_KV key `maintenance:branch-keep`, a JSON object of namespace to branch names (for example `{"dustinedwards": ["review/grok"]}`), empty when unset: a branch on it is never pruned and never listed. A keep list that is not such an object stops the branch rules for that run as `branches-not-checked`, as does a failed GitHub read, and stale branches are not listed when the open pull request list was not read in full. `maintenance_branches_read` is the number of branches the pass read in that namespace, null when it read none. test/maintenance.test.ts guards each branch rule: "with the auto-prune off, a merged branch is listed with a count and nothing is deleted", "with the auto-prune on, the merged branch is deleted and audit-logged, and a keep-listed or open one is not", "the pass deletes at most 25 merged branches per repo per run" and "a failed branch read or an unreadable keep list is listed as not checked"; test-integration/maintenance.test.ts sees the audit row land in D1.

The release-tag rule (src/maintenance-releases.ts; Capsid improvement list, item 13) lets a shared package release without a desk: a cloud session cannot push a tag, and merging the version bump is the release decision. For each `shared_packages` row it reads the repo's root `package.json` version on the default branch through the App, and when no tag names that version and it is newer than every release tag, it tags `v<version>` at the commit that set it (the oldest of the newest run of commits to `package.json` carrying that version, within the last 20; not found is listed, never guessed). A version below the newest tag is never tagged and is listed as `release-backwards`; a pre-release is listed for a person. A release is published too only when `CHANGELOG.md` at that commit has a section for the version; otherwise the tag alone. GitHub refuses an existing tag, so nothing is retagged or moved. At most 3 tags per run, each audit-logged (actor `system:maintenance`, action `maintenance-release-tag`, with the repo, package, tag, sha and release) before the next and listed as `release-tagged`; a tag made through the App's token fires the package's `bump-consumers` workflow. The seat turns it off with `npx wrangler kv key put --binding APP_KV --remote maintenance:release-tags off`; off, or over the cap, an untagged version is listed as `release-untagged`, and a failed read as `releases-not-checked`. test/maintenance-releases.test.ts guards each case.


The undeployed-merge rule (src/maintenance-deploys.ts) reads the watcher's last snapshot, whose Cloudflare read already holds each site's newest deployment, and each site's default branch head through the App. `undeployed-merge` is a site whose newest deployment is older than that head's commit, when the commit is more than 2 hours old and the site's health route does not report its sha. A site on Vercel is left out; a site Cloudflare was not read for, with no deployment, or whose default branch was not read is `deploys-not-checked`, as is no snapshot at all (under capsid). `deploys_read` counts the sites compared. test/maintenance.test.ts guards it ("a live Worker older than its default branch's last commit is listed").

The model drift rule (src/model-drift.ts) compares system/model.json with the namespace mapping, the App's repo list and the watched sites, both ways. `model-drift` is a mapped or installed repo the model does not name, a repo the model names that the App does not list, a system marked public whose repo GitHub reports private, or a watched site whose host is no system's domain. Private repos with no public product are listed in the Capsid document capsid/system/unlisted.md and skipped, so the public model never names them. An unread App list is `model-not-checked`. `model_read` counts the facts compared. test/model-drift.test.ts guards the comparison; test-integration/maintenance.test.ts guards the reads. Details: docs/public-data.md.

The rule document rule (src/rule-docs.ts) reads every namespace's rule documents (docs/schema.md, "Rule documents are held to their cap and to served tool names"). `rule-doc` is one that is over its cap (core.md 8 KB, the others 20 KB) or names a tool or action the Worker does not serve, with the first five such names. `rule_docs_read` counts the rule documents read; a failed read is `rule-docs-not-checked`. test-integration/maintenance.test.ts guards it ("PLANT: lists an over-cap rule document and one naming a stale tool").

The Portal shows the list on Health as the Maintenance panel, from `GET /portal/api/maintenance` (docs/portal.md).

The gate class of a wait is the gate policy's own classifier (`classifyCommand`, src/gate-policy.ts) run over the command the job blocked on: `push_branch`, `open_pr`, `additive_migration` (a compound joined with `+`), `needs_human` for a command that matches none or a gate with no command, `unreadable_gate` for a gate row whose detail is not JSON. It says which waits the signed policy could have approved. It does not say why a person was needed. Waits are measured only from 2026-09-30, when `job_touches` begins.

The `capsid_admin_read_claims` tool reads them, admin only: `action: "job"` with an `id` returns one job's outcome, claims, evaluations and touches; `aggregate` counts agreement and touches per agent and namespace, ranks the ended waits (`waits`: per namespace, gate class and who ended the wait, with count, total and median) and sums usage per namespace (`usage`: telemetry from `job_outcomes` and the agent's reported `claim.usage`, side by side and never added); `export` pages one table by id. `scripts/export-claims.ts --out <dir>` runs that export for `job_claims`, `job_evaluations`, `job_touches` and `job_outcomes` into one JSONL file per table, with `manifest.json` (the Worker's sha, each file's row count and sha256) and `manifest.sha256`. It reads the admin key from `CAPSID_OPERATOR_KEY` only, and refuses a directory that is not empty. `--verify <dir>` recomputes every hash and exits 1 on any mismatch or missing file.
